# Authentication evidence

The API uses Better Auth 1.7.4, its Drizzle adapter 1.7.4, the Expo server plugin 1.7.4, and Drizzle ORM 0.45.2. The runtime factory is `apps/api/src/auth/index.ts`; request guards are in `apps/api/src/auth/session.ts`.

The schema was generated with the installed, version-matched Better Auth CLI on 2026-09-13:

```sh
vp exec auth generate --config apps/api/src/auth/schema-cli.ts --adapter drizzle --dialect sqlite --output apps/api/src/db/auth-schema.ts --yes
```

The shared schema options load the same Expo plugin and database rate limiter in the generator and runtime. Drizzle Kit owns the resulting SQL migrations alongside application tables. D1 does not provide interactive transactions, so the adapter explicitly uses `transaction: false`. Application inventory and payment atomicity must use D1 batch transitions independently of authentication.

Email/password registration requires email verification before a session is issued. Verification and reset links expire after one hour. A password reset revokes existing sessions, and protected API requests read the database rather than trusting a cached session cookie. The verified-session guard also checks current account suspension. Every application operation still needs its own ownership or permission check.

`apps/api/src/auth/permissions.ts` checks current event and platform grants. Event owners can manage their events, organizer support, refunds, analytics, and history. Scanning, reversals, and conflict review require explicit event grants even for the owner. An event grant never supplies a platform permission. Private event access requires an accepted invitation tied to the current verified email, event ownership, a current staff grant, or an explicit platform moderation grant. Token expiry limits acceptance; access from an invitation accepted before that deadline remains valid until revoked. Drafts and suspended events are hidden from public readers. Mutations must repeat relevant permission conditions inside their atomic database transition to cover concurrent revocation.

`AUTH_URL` is the externally reachable API origin and defaults to `APP_ORIGIN` for same-origin deployments. The Google OAuth redirect is `<AUTH_URL>/api/auth/callback/google`. The configured web origin and `elc://` callback scheme are trusted; the local environment also allows `exp://`. Nonlocal authentication requires HTTPS. Cookie-authenticated application mutations need origin checks in the Hono application in addition to Better Auth's auth endpoint checks.

Resend credentials enable email delivery. An explicitly injected transport supports a private local/test mailbox. Without either, email-dependent authentication endpoints return `503 EMAIL_UNAVAILABLE`. Unconfigured Google sign-in returns `503 GOOGLE_UNAVAILABLE`. Provider response bodies, reset links, verification links, and passwords are not logged. Resend requests use stable digest-based idempotency keys for retries of the same email.

The D1 tests run Better Auth in the test process against a Miniflare D1 binding. They verify the real adapter, SQL schema, and authentication behavior, but do not replace a bundled Worker request test or browser/native acceptance.

Configuration follows the current [Better Auth Drizzle adapter](https://better-auth.com/docs/adapters/drizzle), [CLI generation](https://better-auth.com/docs/concepts/cli), and [Drizzle D1](https://orm.drizzle.team/docs/sqlite/connect-cloudflare-d1) documentation. The [Expo integration](https://better-auth.com/docs/integrations/expo) requires native application API calls to attach the SecureStore cookie explicitly. Email verification and reset hooks follow [Better Auth email/password authentication](https://better-auth.com/docs/authentication/email-password), with [Resend's email API](https://resend.com/docs/api-reference/emails/send-email) as the configured transport. The [database rate limiter](https://better-auth.com/docs/concepts/rate-limit) uses shared state across Worker instances.
