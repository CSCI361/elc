# Canonical notification sources

Implemented and verified against isolated D1/R2 resources on 2026-09-13. All 15 source integration tests, scoped format/lint/type checks and the API TypeScript check pass. The loader is `createDeliverySources(env, { fontBytes })` in `apps/api/src/delivery/sources.ts`. It exposes `readCurrent(delivery)` and `prepare(delivery, current)`. The queue coordinator owns transport, leases and retries; this loader never sends email or issues tickets.

Every read matches the supplied delivery envelope against its persisted `email_deliveries` row and joins its original `outbox` source. Source kind, entity and required payload identifiers must agree with the canonical resource. A delivery needs a currently verified, unsuspended recipient and current ownership or case authority. A queue message cannot select another recipient, event, order or support case. Missing resources, revoked access and superseded eligibility return no current delivery.

| Delivery kind          | Canonical source and eligibility                                                                                                                                                                                                                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `order.tickets`        | `order.completed`, matching order ID. Current purchaser, completed order, valid or checked-in tickets, no admission block, cancellation, suspension or refund record. Paid orders require their succeeded, amount-matching payment. Metadata must identify the exact ordered six-ticket partition.                                        |
| `payment.failed`       | `payment.failed`, matching attempt ID. Canonical failed attempt, matching purchaser or activation owner, no completed subject or later succeeded attempt.                                                                                                                                                                                 |
| `activation.completed` | `activation.completed`, source entity is the event and payload identifies the successful fee attempt. Current organizer, active unsuspended event and activation record, confirmed payment, no refund or reconciliation error.                                                                                                            |
| `refund.completed`     | `refund.changed` with the matching refund/attempt and succeeded state. The canonical full refund is confirmed against its succeeded payment. Order refunds go to the purchaser; activation refunds go to the current organizer. Compensated orders need not have completed.                                                               |
| `event.updated`        | `event.changed` with action `event.updated`. Current completed, unblocked purchaser order predating the notice; no cancellation/suspension or later event update/cancellation source.                                                                                                                                                     |
| `event.cancelled`      | `event.changed` with action `event.cancelled`. A currently owned order completed before the notice remains eligible after the cancellation sweep refunds or cancels it.                                                                                                                                                                   |
| `payout.status`        | `payout.simulated` or the linked `payout.adjusted` record. Only the current payout/event owner receives the simulated amount. Adjustments require their confirmed refund and exact payout-item link.                                                                                                                                      |
| `support.changed`      | `support.notify` and the exact case change/sequence. Current requester, authorized assignee or responsible staff; the change author is excluded. An absent or no-longer-authorized assignee allows fallback staff. Event roles never grant access to organizer-platform conversations. Obsolete status/assignment notices are suppressed. |
| `order.cancelled`      | `registration.cancelled`, matching the purchaser's previously completed free registration and its canonical cancellation/admission block.                                                                                                                                                                                                 |

`currentSupportAssigneeSql` exposes the same active-account and staff-authority test for fanout. Assignment alone never grants case access. The source query selects case routing/status metadata and immutable change references; it does not read the subject, message body or attachments for email. Templates provide a generic notice with a protected case link.

The frozen version covers the destination email, saved locale (Kazakh fallback), sender, application origin, rendered template output, canonical ownership/state and immutable delivery binding. Ticket messages also hash each selected PDF's canonical data, token hash, encrypted-credential hash, renderer version and copied font bytes. Polling time, queue attempts and incidental transport timestamps do not change the version. Templates therefore invalidate a frozen message when their actual output changes, without a separate template-version counter.

PDF preparation reloads that same source and rejects an old version. It calls the existing authorized `downloadTicketPdf` for at most six canonical tickets, using the saved locale and private R2 cache. A count/state query plus a six-row partition read bounds the loaded ticket array. The transport bounds each decoded PDF to 2 MiB and the total encoded attachment size to 12 MiB. Base64 conversion uses bounded chunks. The opaque admission credential appears only inside the required private PDF; it is absent from email text, subject, filename and version metadata. Preparation checks the current source again after rendering/R2 work. The coordinator repeats the check before transport.

The focused integration tests use the complete migration chain, real Miniflare D1/R2 bindings and the existing checkout, paid/zero completion, activation, support, cancellation, refund and payout services. Provider results are injected sandbox fixtures; no provider network request is made. Tests cover:

- All three saved locales, canonical A4 PDF bytes and private cache reuse, with no additional ticket issuance.
- Seven tickets delivered as six PDFs and one PDF, followed by authorized free cancellation suppressing both old ticket messages.
- Wrong or changed delivery bindings, recipients, partitions and source payloads; current destination/locale/PDF changes; verification loss and account suspension.
- Verification revocation between the envelope and PDF source query, and revocation during a real R2 write. Neither yields a releasable email request.
- Completed-order cancellation/refund, late-payment compensation without issuance, activation confirmation and late-activation compensation.
- Superseded event notices, separate event-staff and platform-support access, author exclusion, revoked-assignee fallback and stale status changes.
- A failed payment followed by authoritative success, payout-owner authorization and a real linked refund adjustment.

The source tests run the application loader in the test process while using workerd-backed D1/R2. They do not establish external inbox delivery, provider acceptance, spam placement or a deployed Worker transport. Those remain separate delivery acceptance. The earlier [ticket export evidence](ticket-exports.md) covers the renderer's Worker HTTP and visual/QR checks. Tests dispose their isolated resources and do not alter the running development database.
