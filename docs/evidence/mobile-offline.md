# Native offline cache and journal

Implemented on 2026-09-13, following the offline admission policy in `architecture-decisions.md`. This evidence covers local encrypted-file tests, contract/controller tests and native JavaScript bundles. It does not claim that an iPhone or Android device has completed offline acceptance.

## Behavior

`apps/mobile/src/offline` contains the pinned ES256 verifier, encrypted database adapter, account vault, transactional journal, typed Hono API/controller and localized workspace. The existing scanner now accepts provisional offline captures in that workspace. Its online request path keeps an uncertain request separate and reuses its original operation ID and body on retry. Before an online request, a hash-only barrier prevents an older snapshot from admitting the same ticket locally. A pending local admission also blocks a new online scan. Confirmed online admission or refusal stays overlaid on the cached state until an authoritative fresh snapshot permits correction. Uncertain online barriers survive restart; recapturing the same QR online reuses the stored operation ID without storing the credential.

The database applies a random 256-bit SQLCipher key before reading the schema, verifies `cipher_version`, and fails closed when encryption or an existing protected key is unavailable. Each account, API origin and environment receives a separate encrypted file and SecureStore key. The native key uses `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. The runtime has no plaintext fallback. All queries share one private keyed connection and a serial queue; writes use `BEGIN IMMEDIATE`. This avoids Expo's exclusive transaction helper opening a second connection without the runtime key.

Snapshot installation requires a deployment-pinned ES256 signature, every ordered page digest, unique ticket IDs/hashes, matching account/device/event bindings and valid expiry. Out-of-order downloaded pages are accepted only after assembling the complete signed set. The key pin is public. No server-supplied key, raw admission credential or contact detail is cached. The database stores attendee names, hashes and the state necessary for scanning; lookup displays names without granting admission by name.

A snapshot expires four hours after issuance, capped at event end plus two hours. Event admission stops at event end. Connected prepared events refresh every minute; new snapshots preserve pending operations. Reconnection requests a new snapshot even when cleanup has removed an expired one. Known event cancellation, permission denial and device revocation invalidate cached admission. Offline UI eligibility uses the signed time estimate, so an ahead-skewed wall clock does not override a freshly authenticated anchor. Clock rollback sets a persisted unsafe flag and deletes snapshots. Restart or account reauthentication alone cannot clear it; a newly authenticated snapshot/time anchor is required.

The capture timestamp sent to the server is signed issuance time plus elapsed client time, including the snapshot request/download interval so network latency cannot extend expiry. The encrypted journal retains the raw wall-clock capture separately. Running checks compare wall time with a monotonic clock. Persisted wall high-water marks catch rollback across restart. Capture timestamps never determine server admission priority.

A local transaction records each attempted scan and admits a ticket at most once on that device. An unsent undo is paired with its scan in the same sealed unit. A batch contains at most 25 units. Once sealed, its payload and IDs survive restart and cannot gain a late undo. Response validation requires the exact complete operation set and verifies that a paired undo never produces an admission. An uncertain response retains the same batch for replay. Current server rules decide confirmation or conflict, including uploads by staff whose assignment was revoked after capture.

Sign-out first removes the protected active-account marker, then deletes snapshots and locks the journal. A same-account online proof is required to unlock it. Account switching locks the previous vault, and in-flight work cannot install a snapshot after a logout generation change. Inactive-account maintenance can delete expired records but cannot expose them to the current account or upload them.

Acknowledged operations and their duplicate attempt metadata expire after 24 hours. Unacknowledged operations expire after seven days, with a warning after 24 hours and a visible deletion deadline. Expiring part of a sealed batch removes its old payload; surviving units retain their original operation IDs and sealed status when repackaged. Cleanup runs on startup, every 30 seconds and on foregrounding. It cannot run while a device is powered off. Secure deletion and WAL truncation reduce retained database content; flash-device forensic erasure is not claimed.

## Executed checks

- `vp test run apps/mobile/src`: 46 tests passed across six files. The new offline unit accounts for 33 tests.
- Actual SQLCipher tests opened encrypted files, verified that file bytes lacked SQLite's plaintext header and fixture attendee/credential text, rejected a wrong key, and recovered the same journal with the correct key. Tests also used two concurrent connections to prove one local provisional admission.
- Store tests cover invalid/unknown/refunded/cancelled/already-used credentials, refresh without journal loss, paired undo, partial acknowledgements, interrupted/replayed sync, 25-unit batching, logout/restart, rollback persistence, acknowledgement clock skew, 24-hour cleanup, seven-day cleanup and partial sealed-batch expiry. Five review regression tests cover online/offline admission barriers, persisted uncertain operation IDs, known refund outcomes, trusted-time eligibility and barrier retention.
- Vault tests cover protected-key loss, API-origin isolation, different-account denial, same-account recovery, a delayed proof racing logout, and deletion of a signed-out journal without uploading it.
- Verifier tests accept WebCrypto signatures with either valid S representation and reject missing/duplicated/tampered pages, wrong keys/bindings, private pins, expiry and correctly signed duplicate ticket hashes.
- Controller tests cover complete snapshot download, stable device-registration receipts, conservative time anchoring, exact network-ambiguity replay, revocation/cancellation during refresh, denied upload acknowledgement and online account mismatch.
- Mobile TypeScript and scoped `vp check` pass. `expo install --check` reports dependencies up to date.
- `vp run --filter @elc/mobile bundle` exported iOS and Android Hermes bundles with Metro: approximately 3 MB per platform.
- Expo public configuration contains native iOS/Android targets and `expo-sqlite` with `useSQLCipher: true`. The local signing pin is `local-v1`; its public JWK has no private `d` member.

## Dependencies and acceptance limits

Runtime pins are Expo SQLite 57.0.3, Noble Curves/Hashes 2.4.0 and Expo SecureStore 57.0.4. The host test module is `@journeyapps/sqlcipher` 6.0.0, reporting SQLCipher `4.14.0 community`, built from source with node-gyp 12.3.0 and the installed macOS command-line tools/CommonCrypto. It exercises actual SQLCipher files, not an in-memory storage mock. The protected-storage boundary is injected in host tests; native Keychain/Keystore behavior still requires device verification.

The implementation follows the [Expo SQLite documentation](https://docs.expo.dev/versions/latest/sdk/sqlite/), [Expo SecureStore documentation](https://docs.expo.dev/versions/latest/sdk/securestore/), [Noble Curves source and API](https://github.com/paulmillr/noble-curves), and [JourneyApps SQLCipher build instructions](https://github.com/journeyapps/node-sqlcipher). Expo Go does not support the required SQLCipher configuration.

This host has command-line tools rather than the full Xcode/simulator installation, and no Android adb/emulator setup. The required physical iPhone and Android checks remain pending: native SQLCipher/SecureStore startup, camera and grayscale-ticket scans, two disconnected phones admitting the same ticket, process/device restart, background cleanup, reconnect conflicts, refunds/revocation during disconnection, lost-device recovery and minimum-OS behavior. Record device models, OS versions and build identifiers when those checks are executed. Google sign-in also remains pending configured external-provider acceptance.
